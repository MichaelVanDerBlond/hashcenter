# HashCenter Project Specification

**Version:** R0.1
**Status:** Active
**Priority:** Highest

---

# Назначение документа

Данный документ является главным архитектурным документом проекта HashCenter.

Любой разработчик (человек или ИИ), прежде чем изменять код проекта, обязан ознакомиться с данным документом.

Если предлагаемые изменения противоречат этому документу, приоритет всегда имеет настоящий документ.

---

# Философия проекта

HashCenter — это профессиональный центр управления процессами Hashcat.

Проект не является:

- GUI для Hashcat;
- набором bash-скриптов;
- оболочкой для запуска команд;
- коллекцией отдельных утилит.

HashCenter является самостоятельной системой управления жизненным циклом задач подбора паролей.

---

# Главная цель

Максимально автоматизировать весь процесс работы с Hashcat:

- анализ входных данных;
- определение типа захвата;
- конвертация;
- выбор словарей;
- управление задачами;
- мониторинг;
- история;
- масштабирование.

HashCenter должен быть способен выполнять эти задачи без ручного вмешательства пользователя.

---

# Главные архитектурные принципы

Каждый пакет имеет только одну ответственность.

Каждая подсистема отвечает только за свою область.

Запрещены циклические зависимости.

Каждый уровень архитектуры знает только о следующем уровне.

Любое изменение должно быть минимальным.

Работающий код не переписывается без объективной причины.

# Ответственность уровней

## Web

Отображение информации.

Не содержит бизнес-логики.

Не работает напрямую с SQLite.

Не запускает Hashcat.

---

## Handlers

Получают HTTP-запрос.

Проверяют входные данные.

Вызывают Service.

Возвращают ответ.

---

## Services

Основная бизнес-логика.

Не знают ничего о HTTP.

Не содержат SQL.

---

## Repository

Работа с постоянным хранением данных.

Не содержат бизнес-логики.

---

## Database

Только хранение данных.

---

## Hashcat Engine

Отвечает исключительно за взаимодействие с Hashcat.

Не знает о Web.

Не знает о HTTP.

# Правила разработки

Запрещается:

- писать SQL в Handler;
- запускать Hashcat из Web;
- хранить бизнес-логику в HTTP;
- обращаться к SQLite напрямую из интерфейса;
- использовать глобальные переменные без крайней необходимости;
- создавать дублирующий функционал.

---

# Правила изменения архитектуры

Любое изменение архитектуры должно отвечать на вопросы:

Почему изменение необходимо?

Какая проблема решается?

Почему существующая архитектура не подходит?

Какие последствия будут для остальных компонентов?

Если хотя бы один ответ отсутствует — изменение считается необоснованным.

---

# Правила для ИИ

Перед написанием любого кода ИИ обязан:

1. Изучить существующую реализацию.
2. Найти уже существующий механизм.
3. Не создавать дублирование.
4. Не менять архитектуру без необходимости.
5. Использовать существующие структуры данных.
6. Использовать существующие интерфейсы.
7. При недостатке информации сначала задать вопрос.
8. Предлагать минимально возможные изменения.
9. Не переписывать работающий код.
10. После внесения изменений убедиться, что проект собирается.

---

# Главный принцип

HashCenter развивается эволюционно.

Каждая новая возможность должна естественно дополнять существующую архитектуру.

Проект не должен усложняться ради красоты кода.

Главный критерий качества — простота, предсказуемость и расширяемость.
