# HashCenter Dependency Rules

Version: R0.1

-------------------------------------------------------------------------------
# Назначение

Документ определяет допустимые зависимости между пакетами проекта.

Главная цель — сохранить архитектуру чистой, исключить циклические зависимости
и обеспечить простое сопровождение проекта.

Любое нарушение этих правил считается архитектурной ошибкой.

-------------------------------------------------------------------------------
# Архитектурная схема

                           Browser
                              │
                              ▼
                         Web Interface
                              │
                              ▼
                           Handlers
                              │
                              ▼
                           Services
                         ╱     │      ╲
                        ▼      ▼       ▼
                 Repository Scanner Hashcat
                        │
                        ▼
                     Database

Поток зависимостей всегда направлен сверху вниз.

-------------------------------------------------------------------------------
# Правило направленных зависимостей

Каждый пакет может знать только о пакетах,
расположенных ниже по архитектуре.

Нижние уровни никогда не знают о верхних.

-------------------------------------------------------------------------------
# Интерфейсы

Если подсистема должна использовать функциональность другой подсистемы,
предпочтительно использовать интерфейс.

Это позволяет:

- уменьшить связанность;
- облегчить тестирование;
- заменить реализацию без изменения бизнес-логики.

-------------------------------------------------------------------------------
# Циклические зависимости

Запрещены полностью.

Если возникает необходимость взаимного импорта,
архитектура считается ошибочной.

Решение:

- выделить общий интерфейс;
- выделить новую подсистему;
- изменить направление зависимости.

-------------------------------------------------------------------------------
# Добавление нового пакета

Перед созданием нового пакета необходимо ответить:

1. Можно ли использовать существующий?
2. Не создаёт ли новый пакет дублирование?
3. Какое место он занимает в архитектуре?
4. Кто будет зависеть от него?
5. От кого зависит он?

Если ответы отсутствуют — новый пакет создавать нельзя.

-------------------------------------------------------------------------------
# Проверка перед Commit

Перед каждым Commit необходимо убедиться:

✓ нет циклических зависимостей

✓ новый импорт оправдан

✓ слой архитектуры не нарушен

✓ бизнес-логика не ушла в Handler

✓ SQL не появился вне Repository

✓ Hashcat не вызывается напрямую из Web

✓ Scanner не изменяет Database

-------------------------------------------------------------------------------
# Правила для ИИ

Перед добавлением import ИИ обязан определить:

- зачем нужен импорт;
- существует ли уже аналогичная зависимость;
- нарушает ли импорт архитектурные правила;
- можно ли использовать интерфейс вместо прямой зависимости.

Если импорт нарушает данный документ,
код должен быть переработан до написания.

-------------------------------------------------------------------------------
# Главный принцип

Зависимости проекта должны оставаться простыми,
однонаправленными и предсказуемыми.

Любая сложность должна находиться внутри компонентов,
а не в связях между ними.
