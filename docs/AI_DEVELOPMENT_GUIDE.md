# AI Development Guide

Version: R0.1

-------------------------------------------------------------------------------
# Назначение

Данный документ определяет обязательный порядок работы искусственного
интеллекта при разработке HashCenter.

Цель документа — обеспечить единый стиль разработки независимо от модели ИИ.

Любое отклонение от данного алгоритма считается ошибкой.

-------------------------------------------------------------------------------
# Главный принцип

ИИ не пишет код.

ИИ сначала изучает проект.

Код является последним этапом.

-------------------------------------------------------------------------------
# Алгоритм работы

Любая задача выполняется строго в следующем порядке.

1. Изучение задачи

↓

2. Изучение архитектуры

↓

3. Поиск существующей реализации

↓

4. Анализ зависимостей

↓

5. Проектирование решения

↓

6. Только после этого написание кода

-------------------------------------------------------------------------------
# Шаг 1

Перед началом работы обязательно изучить:

docs/PROJECT_SPEC.md

docs/PROJECT_STRUCTURE.md

docs/CODEMAP.md

docs/DEPENDENCIES.md

-------------------------------------------------------------------------------
# Шаг 2

Найти существующую реализацию.

Перед созданием нового файла необходимо определить:

существует ли уже аналогичный компонент

существует ли уже аналогичный сервис

существует ли уже аналогичный Repository

существует ли уже аналогичная структура

если существует —
использовать её

-------------------------------------------------------------------------------
# Шаг 3

Определить место изменения.

Ответить:

Какой компонент изменяется?

Почему именно он?

Какие ещё компоненты будут затронуты?

Можно ли ограничиться меньшим количеством файлов?

-------------------------------------------------------------------------------
# Шаг 4

Минимизировать изменения.

Предпочтение всегда отдаётся:

изменению существующего кода

вместо

создания нового.

-------------------------------------------------------------------------------
# Шаг 5

Перед созданием нового файла ответить:

Почему нельзя использовать существующий?

Какую новую ответственность получает файл?

Не создаётся ли дублирование?

-------------------------------------------------------------------------------
# Шаг 6

Перед созданием нового пакета ответить:

Почему существующие пакеты не подходят?

Какие зависимости появятся?

Не нарушается ли архитектура?

-------------------------------------------------------------------------------
# Запрещается

Переписывать работающий код.

Менять архитектуру без необходимости.

Создавать новый пакет без причины.

Создавать новый Service,
если уже существует подходящий.

Создавать новый Repository,
если можно расширить существующий.

Переносить код между пакетами
без архитектурного обоснования.

-------------------------------------------------------------------------------
# Перед изменением структуры данных

Определить:

кто использует структуру

где она сериализуется

где хранится

где отображается

что изменится после модификации

-------------------------------------------------------------------------------
# Перед добавлением import

Определить:

не создаёт ли import циклическую зависимость

не нарушает ли слой архитектуры

можно ли использовать интерфейс

-------------------------------------------------------------------------------
# После написания кода

Обязательно выполнить:

go fmt ./...

go vet ./...

go test ./...

После успешной проверки:

убедиться

что

код соответствует

PROJECT_SPEC.md

PROJECT_STRUCTURE.md

DEPENDENCIES.md

-------------------------------------------------------------------------------
# Если информации недостаточно

Не придумывать.

Не делать предположений.

Остановиться.

Сформулировать вопрос разработчику.

-------------------------------------------------------------------------------
# Главный критерий качества

Лучшее изменение —

то,

которое:

затрагивает минимум файлов;

использует существующую архитектуру;

не создаёт новых зависимостей;

не создаёт дублирования;

не требует переписывания работающего кода.
