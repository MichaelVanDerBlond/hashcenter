# HashCenter Development Workflow

Version: R0.1

===============================================================================
Назначение
===============================================================================

Документ определяет единый процесс разработки проекта HashCenter.

Данный процесс обязателен для:

• разработчиков;

• AI Assistant;

• Aider;

• Claude Code;

• ChatGPT;

• Gemini;

• DeepSeek;

• любых других инструментов разработки.

===============================================================================
Главный принцип
===============================================================================

Сначала понять.

Потом проектировать.

Потом писать код.

Никогда наоборот.

===============================================================================
Этап 1
Получение задачи
===============================================================================

Определить:

Что необходимо реализовать.

Какую проблему необходимо решить.

Какие требования существуют.

Какие ограничения существуют.

===============================================================================
Этап 2
Изучение документации
===============================================================================

Обязательно ознакомиться с:

docs/AI_CONTEXT.md

docs/PROJECT_SPEC.md

docs/PROJECT_STRUCTURE.md

docs/CODEMAP.md

docs/DEPENDENCIES.md

===============================================================================
Этап 3
Изучение существующего кода
===============================================================================

Найти:

существующий Handler

существующий Service

существующий Repository

существующие структуры

существующие интерфейсы

существующие тесты

Запрещается писать новый код,
не изучив существующий.

===============================================================================
Этап 4
Проектирование
===============================================================================

Ответить:

Что изменяется?

Почему?

Какие файлы будут изменены?

Какие зависимости появятся?

Можно ли сделать проще?

===============================================================================
Этап 5
Реализация
===============================================================================

Использовать существующую архитектуру.

Изменять минимальное количество файлов.

Не создавать дублирование.

Не менять публичное API без необходимости.

===============================================================================
Этап 6
Самопроверка
===============================================================================

Проверить:

нет ли дублирования;

не нарушена ли архитектура;

не появились ли циклические зависимости;

не нарушены ли правила именования.

===============================================================================
Этап 7
Проверка проекта
===============================================================================

Выполнить:

go fmt ./...

go vet ./...

go test ./...

go build ./...

При наличии интеграционных тестов выполнить и их.

===============================================================================
Этап 8
Проверка документации
===============================================================================

Если изменилось:

архитектура

структура проекта

новая подсистема

новый термин

новый поток данных

обязательно обновить соответствующую документацию.

===============================================================================
Этап 9
Git
===============================================================================

Перед Commit убедиться:

код собирается;

тесты проходят;

документация актуальна.

Commit должен описывать одно логическое изменение.

Не объединять несколько независимых изменений в один Commit.

===============================================================================
Этап 10
Review
===============================================================================

Перед завершением работы ответить:

Решена ли задача?

Не нарушена ли архитектура?

Можно ли сделать проще?

Не усложнил ли код проект?

===============================================================================
Контрольный список
===============================================================================

□ Изучена документация

□ Изучен существующий код

□ Определена точка расширения

□ Архитектура сохранена

□ Нет дублирования

□ Минимальное количество изменений

□ Код отформатирован

□ Проверки выполнены

□ Документация обновлена

□ Commit готов

===============================================================================
Главное правило
===============================================================================

Каждое изменение должно делать проект
проще,
понятнее,
надёжнее
и легче для дальнейшего развития.

Если изменение не соответствует этим критериям,
его необходимо пересмотреть до объединения с основной веткой.
